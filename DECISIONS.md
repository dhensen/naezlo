# Decisions

Decisions that `README.md` does not cover. Append new ones at the bottom with a date and the story ID.

## Stack (2026-11-14, before US-001)

- **Backend** lives at the repo root: Python 3.14, uv, FastAPI, SQLAlchemy 2 (async) with asyncpg, Alembic, pydantic-settings, Authlib for Google login, the official `mcp` Python SDK for the MCP server. Package in `src/todolist/`.
- **Database**: PostgreSQL 18 through `docker compose`. Tests run against a real Postgres test database, each test inside a transaction that is rolled back. No SQLite.
- **Frontend** lives in `frontend/`: Vite, React, TypeScript (strict), React Router, TanStack Query, Tailwind CSS. API types are generated from FastAPI's OpenAPI schema. Package manager is npm (pnpm is not installed on this machine).
- **Serving**: in development Vite proxies to the backend; in production FastAPI serves `frontend/dist`.
- **Quality checks**
  - Backend: `uv run ruff check`, `uv run ruff format --check`, `uv run pyright`, `uv run pytest`
  - Frontend (once `frontend/` exists, US-027): `npm --prefix frontend run lint`, `npm --prefix frontend run typecheck`, `npm --prefix frontend run test`
  - End to end (once US-029 exists): `npm --prefix frontend run e2e`
- **Login without Google credentials**: the loop has no Google OAuth client. Google is mocked in tests. A dev-login endpoint, enabled only when `DEV_LOGIN=true`, is used for local runs and end-to-end tests. It must be off by default.
- **Secrets** come from environment variables. `.env` is git-ignored; `.env.example` documents every variable with safe placeholder values.

## Domain (2026-11-14, before US-001)

- **Tenancy**: `User`, `Organization`, `Membership` with role `owner | admin | member`. A new user gets a default organization on first sign-in. Invitations are by email and are accepted automatically on the invitee's next sign-in; v1 sends no email.
- **Agents**: an `Agent` belongs to one organization and is a principal like a user. Code that checks permissions or records audit events takes a `Principal` (kind `user | agent`), never a bare user.
- **Hierarchy**: `Organization` → `Project` → `TodoList` → `Item`. An item has a title, notes, status `open | done` and a position.
- **ACL**
  - Grants exist on projects and on lists, for a user or an agent, with role `viewer | editor | admin`. List grants also allow `none`.
  - Effective role on a list: the list grant if there is one, otherwise the project grant.
  - Organization owners and admins are admin on everything in their organization.
  - No role means the resource does not exist for that principal: respond 404, not 403. Use 403 when the principal can see the resource but the action needs a higher role.
- **List mode**: `human_only | ai_only | mixed`.
  - Default for a new list: `mixed` when the organization has at least one agent, otherwise `human_only`.
  - `human_only`: agents have no access, whatever their grants.
  - `ai_only`: humans can read according to their role but cannot change items. List admins can still rename the list, change its mode and manage its grants.
  - `mixed`: both act according to their role.
- **Audit log**: one `audit_events` table with organization, project, list (nullable), actor kind, actor id, actor name snapshot, action, target and JSON details. Events are written in the same transaction as the change and survive deletion of their target.
- **MCP**: streamable HTTP at `/mcp`. The app is its own OAuth 2.1 authorization server (metadata discovery, dynamic client registration, PKCE with S256, refresh token rotation, revocation). On the consent screen the signed-in user picks which agent the client acts as; that requires being owner or admin of the agent's organization. Tokens are stored hashed and resolve to that agent. MCP tools and the HTTP API share the same service functions.
- **Not in v1**: billing, sending email, password login. The product name ("needs a better name" in the README) is a human decision; keep `todolist` as the working name and keep it in one place per layer (a setting in the backend, a constant in the frontend).

## Database plumbing (2026-11-14, US-002)

- **Host port 5435** for the compose Postgres (override with `POSTGRES_PORT`; then also set `DATABASE_URL` and `TEST_DATABASE_URL`). Ports 5432 to 5434 are used by other projects on the development machine. The compose credentials (`todolist` / `todolist`) are local-only defaults, not secrets.
- **Primary keys** are UUIDv7 generated in Python (`uuid.uuid7`), so ids are known before the flush and sort by creation time.
- **Timestamps** are `timestamptz`, set by the database (`now()`).
- **One transaction per request**: `get_session` commits when the handler returns and rolls back when it raises. Routes use `SessionDep`, which has `scope="function"` so the commit happens before the response is sent. Services flush; they don't commit.
- **Alembic** lives in `migrations/` with an async `env.py`. The URL comes from `Settings.database_url`; nothing is stored in `alembic.ini`. New revision files are formatted and lint-fixed by ruff through post-write hooks.
- **Test database**: the test session drops and recreates the `public` schema of `todolist_test` and migrates it to head, so every run also proves that migrations work on an empty database. The app under test gets `database_url = test_database_url`.

## Tenancy models (2026-11-14, US-003)

- **Emails** are stored trimmed and lowercased. The `User` model normalizes on assignment and a check constraint (`email = lower(email)`) guards the column, so the plain unique constraint is case-insensitive in effect. Look users up with `normalize_email(...)`.
- **Enums** are native PostgreSQL enum types that store the lowercase values (`owner`, not `OWNER`), built with `todolist.db.value_enum`. Python side: `enum.StrEnum`.
- **Deleting a user** deletes their memberships (`ON DELETE CASCADE`), like deleting an organization does. v1 has no user deletion feature; this only keeps the schema consistent.
- **Relationships** are declared with `lazy="raise"`: async code cannot lazy-load, so a forgotten `selectinload` fails loudly instead of with `MissingGreenlet`.

## Sessions and sign-in (2026-11-14, US-004)

- **Session**: Starlette `SessionMiddleware`, a signed cookie named `session` that holds only the user id (14 days, HttpOnly, SameSite=Lax). It is `Secure` when `ENVIRONMENT=production`; development and tests run on plain http.
- **`SESSION_SECRET`** has an insecure development default so a fresh checkout runs. With `ENVIRONMENT=production` the app refuses to start when the secret is unset, and also when `DEV_LOGIN=true`: dev-login signs in as any email address without a password.
- **Dev-login when disabled** answers 404 to every request, before the body is validated, like a route that does not exist. The route stays in the OpenAPI schema so the generated frontend types do not depend on the environment.
- **Error body**: `{"detail": "<message>", "code": "<snake_case>"}`. Raise a `todolist.errors.AppError` (or a subclass); clients branch on `code`. FastAPI's own errors (422 validation, unknown route) have `detail` only.
- **Default organization**: named "<name>'s organization", slug derived from the user's name ("Ada Lovelace" → `ada-lovelace`). Slugs are ASCII `[a-z0-9-]`; a taken slug gets a number (`ada-2`, `ada-3`), and a name without usable characters becomes `org`.
- **`get_or_create_user`** finds a user by `google_sub` when one is given, otherwise by email. An existing user keeps their stored name and email; a missing `google_sub` is filled in. Only creation makes a default organization.
- **`/api/me` and dev-login** return `{"user": {...}, "organizations": [{id, name, slug, role}]}`, organizations in the order the user joined them.
- **Correction to "Primary keys" above**: the UUIDv7 default is applied by SQLAlchemy at flush time, so `obj.id` is `None` until the first flush. Link new objects through relationships (`Membership(organization=org, ...)`) or flush first.

## Google login (2026-11-14, US-005)

- **Client**: Authlib's Starlette OpenID Connect client behind `todolist.google.GoogleClient` (Authlib has no type information). Endpoints and signing keys come from Google's discovery document; the flow uses state, nonce and PKCE (S256), all kept in the session cookie. Scope: `openid email profile`.
- **HTTP library**: `httpx2` is a runtime dependency because Authlib 1.9 uses it and deprecates plain `httpx`. `httpx` stays a dev dependency for the test client.
- **`PUBLIC_BASE_URL`** (default `http://localhost:8000`) is the URL people open in their browser. The Google redirect URI is `<PUBLIC_BASE_URL>/api/auth/google/callback`, never derived from the Host header. US-020 uses the same setting for the OAuth issuer.
- **Failures redirect, they don't return JSON**: both Google routes are opened by browser navigation, so a failed sign-in goes to `/login?error=<code>` with code `google_login_failed` (bad or reused state, refusal at Google, invalid ID token), `email_not_verified`, `google_account_conflict` or `google_unavailable`. The login page (US-028) should show a message for these. When Google login is not configured both routes answer a JSON 404 like any unknown route.
- **`next`** must start with a single `/` and contain no backslash or control character; anything else is ignored and the user lands on `/`. It lives in the session under `login_next` and is forgotten when a new login starts without it.
- **Email linked to another Google account**: when the ID token's `sub` is unknown but its email belongs to a user who already has a different `google_sub`, the sign-in is refused (`google_account_conflict`). The address was probably reassigned; signing in would hand over someone else's account.
- **Profile data**: a returning user keeps their stored name and email even when Google reports new ones (found by `sub`). The picture is refreshed on every Google sign-in. `email_verified` must be the JSON value `true`.

## Organization API (2026-11-14, US-006)

- **Shape**: every organization endpoint returns `{id, name, slug, role}`, where `role` is the caller's own role (the same object as in `/api/me`). `POST /api/orgs` answers 201.
- **Names** are trimmed and must be 1 to 200 characters (422 otherwise). Names need not be unique; slugs are.
- **Renaming keeps the slug**, so links that contain it keep working. v1 has no way to change a slug.
- **Not a member means 404**, with the same body as an id that does not exist. A member whose role is too low gets 403 with code `forbidden` (`ForbiddenError`).
- **Organization-level role checks** live in one place: `can_manage_organization(role)` in `services/organizations.py`, applied by the `OrgAdminContextDep` dependency. Routes don't compare roles themselves. The permission service of US-011 (projects and lists, with a `Principal`) should build on this function rather than repeat the rule.

## Organization members (2026-11-14, US-007)

- **Shape**: a member is `{user_id, email, name, role}`, listed in the order people joined. `PATCH` returns the changed member, `DELETE` answers 204. The path id is the user's id, not the membership's.
- **Who may change what**: owners and admins change roles and remove members. Any change that involves the owner role (granting it, demoting an owner, removing an owner) needs an owner; an admin gets 403. Admins can demote and remove other admins. Everyone can remove themselves (leave).
- **Last owner**: demoting or removing the only owner answers 409 with code `last_owner`, also when that owner is the only member. An owner who wants out makes someone else owner first. The owner rows are locked (`FOR UPDATE`) during the check, so two owners can't leave at the same moment.
- **Order of answers**: not a member of the organization → 404; target is not a member → 404 `Member not found`; not allowed → 403; last owner → 409. A member (not owner or admin) who patches gets 403 before the target is looked up.
- **Rules live in the service**: `can_change_member_role` and `can_remove_member` in `services/organizations.py`; `change_member_role` and `remove_member` apply them and raise the `AppError`s themselves, because whether a removal is allowed depends on the target and can't be a route dependency. Conflicts use `ConflictError(code, detail)` with a specific code.

## Invitations (2026-11-14, US-008)

- **Table**: `invitations` with `organization_id`, `email` (trimmed and lowercased, same check constraint as `users.email`), `role`, `invited_by` and the usual timestamps; unique on `(organization_id, email)`. `role` is its own enum type `invitation_role` (`admin | member`): ownership is never given by invitation, so `owner` is a 422. Deleting the organization deletes its invitations; deleting the inviter keeps them (`invited_by` becomes null).
- **Who**: inviting, listing and revoking all need an owner or admin (`OrgAdminContextDep`); a member gets 403. Admins may invite admins, as they may promote members to admin.
- **`POST /api/orgs/{org_id}/invitations`** answers 201 with `{status, message, member, invitation}`. `status` is `added` (the email has an account: `member` is the new member, no invitation is stored) or `invited` (`invitation` is the stored one). `message` says in words what happened, including that no email is sent and the person joins on their next sign-in. `role` defaults to `member`.
- **Conflicts**: the email is a member already → 409 `already_member`; it has a pending invitation in this organization → 409 `already_invited` (revoke and invite again to change the role).
- **Invitation shape**: `{id, email, role, invited_by: {user_id, name} | null, created_at}`, listed oldest first. `DELETE` answers 204, and 404 for an id that is not a pending invitation of this organization.
- **Acceptance**: `get_or_create_user` turns every pending invitation for the user's stored email into a membership on every sign-in, for new users after their default organization is created (so that one stays first) and for existing users too. An invitation to an organization the user is already in is dropped without changing their role. There is no accept or decline step in v1.

## Agents and the Principal type (2026-11-14, US-009)

- **`Principal`** (`todolist.principals`) is the actor type for permission checks and audit events: a frozen dataclass with `kind` (`PrincipalKind`: `user | agent`), `id` (the user's or the agent's id), `organization_id` (the organization the actor acts in) and `name` (the display name at that moment, for the audit log's actor name snapshot). Build one with `Principal.for_user(user, organization_id)` or `Principal.for_agent(agent)`; in an org-scoped route `org.principal` gives the caller's. An agent's organization is the one it belongs to; a user's is the one the request is about. Building a principal checks nothing: the caller has established membership. The permission service (US-011) and audit recording (US-018) take a `Principal`, never a bare `User` or `Agent`.
- **Managing agents is an organization-level rule**, like members and invitations: listing needs any membership (`OrgContextDep`), creating, changing and deleting need an owner or admin (`OrgAdminContextDep`, built on `can_manage_organization`). Only users manage agents in v1, so these routes don't take a `Principal` yet.
- **Table**: `agents` with `organization_id` (cascade), `name` (200), `description` (text, nullable), `created_by` (the user; becomes null when that user is deleted) and timestamps; unique on `(organization_id, name)`.
- **Names** are trimmed, 1 to 200 characters, and unique per organization by exact match (`Claude` and `claude` are two names). A taken name answers 409 `agent_name_taken`. The unique constraint decides (insert or update inside a savepoint), not a query beforehand.
- **Descriptions** are trimmed, at most 2000 characters; an empty one is stored as null.
- **Shape**: `{id, name, description, created_by, created_at, updated_at}`, `created_by` being a user id or null; listed oldest first. `POST` answers 201, `DELETE` 204. `PATCH` changes only the fields that are sent: `description: null` clears it, `name: null` is a 422. There is no `GET` for a single agent (no story needs one yet).
- **Order of answers**: not a member → 404 `Organization not found`; member but not owner or admin → 403 (also for an agent id that does not exist); unknown agent or one of another organization → 404 `Agent not found`.

## Projects (2026-11-14, US-010)

- **Table**: `projects` with `organization_id` (cascade, indexed), `name` (200), `description` (text, nullable), `created_by` (the user; becomes null when that user is deleted) and timestamps.
- **Names** are trimmed, 1 to 200 characters, and need not be unique: two projects in one organization can have the same name. Descriptions are trimmed, at most 2000 characters; an empty one is stored as null.
- **Routes**: `POST` (201) and `GET /api/orgs/{org_id}/projects` create and list; `GET`, `PATCH` and `DELETE` (204) `/api/projects/{project_id}` address a project by its own id, without the organization in the path.
- **Shape**: `{id, organization_id, name, description, created_by, created_at, updated_at}`, `created_by` being a user id or null; listed oldest first. `PATCH` changes only the fields that are sent: `description: null` clears it, `name: null` is a 422. A project cannot move to another organization.
- **Access until US-011**: every member of the organization can create, see, change and delete its projects. Someone who is not a member gets 404 `Project not found`, the same body as for an id that does not exist (and 404 `Organization not found` on the two org-scoped routes).
- **`ProjectContextDep`** (`todolist.api.deps`) resolves `{project_id}` for the signed-in user and gives `ctx.project`, `ctx.membership`, `ctx.user` and `ctx.principal`. US-011 puts the permission service behind it.

## Project ACL and the permission service (2026-11-14, US-011)

- **Table**: `project_grants` with `project_id`, `principal_kind` (`user | agent`, PostgreSQL type `principal_kind`), `user_id`, `agent_id`, `role` (`viewer | editor | admin`, type `project_role`) and timestamps. A check constraint makes exactly the column that `principal_kind` names non-null; unique on `(project_id, user_id)` and on `(project_id, agent_id)`. Grants are deleted with their project, user or agent. The migration gives the creator of every existing project an admin grant.
- **Permission service**: `todolist.permissions`. `effective_project_role(session, principal, project)` (the story writes it without the session; a database lookup needs one) returns `admin` for owners and admins of the project's organization, otherwise the grant's role, otherwise `None`. `role_at_least(role, minimum)` compares roles (`viewer < editor < admin`); `visible_projects(principal)` is the same rule as a query, for lists.
- **A grant needs a membership**: a user's grant counts only while they are a member of the project's organization, and a principal acting in another organization has no role. Removing a member (or leaving) deletes their project grants in that organization, so joining again does not bring old access back.
- **An organization owner or admin is always admin**, also when a grant gives them a lower role.
- **Creating a project** is open to every member of the organization and gives the creator an admin grant. A plain member therefore sees their own projects and the ones shared with them, nothing else.
- **Routes**: `require_project_role(minimum)` in `todolist.api.deps` (aliases `ProjectContextDep` for viewer, `ProjectEditorContextDep`, `ProjectAdminContextDep`). No role → 404 `Project not found`; role too low → 403 `forbidden`. `GET` needs viewer, `PATCH` editor, `DELETE` admin. `ProjectContext` has `role` instead of `membership`.

## Project grants API (2026-11-14, US-012)

- **Routes**: `GET` and `PUT /api/projects/{project_id}/grants`, `DELETE /api/projects/{project_id}/grants/{grant_id}` (204). All three need the admin role on the project (`ProjectAdminContextDep`): 404 `Project not found` without a role, 403 for a viewer or editor.
- **Shape**: `{id, principal_kind, principal_id, name, email, role, created_at, updated_at}`, listed oldest first. `name` is the user's or the agent's current name; `email` is the user's and null for an agent (the sharing dialog needs it to tell people apart).
- **`PUT` is create-or-update** by `(principal_kind, principal_id)` and answers 200 in both cases, with the same grant id after an update. Roles are `viewer | editor | admin`; there is no `none` on a project (revoke the grant instead).
- **Who can get a grant**: a user who is a member of the project's organization or an agent that belongs to it. Anything else (another organization, an unknown id, a user id sent as an agent) answers 422 with code `invalid_principal`, without saying which of those it was.
- **Last admin** (409 `last_project_admin`): revoking or downgrading a user's admin grant is refused when afterwards no person could administer the project, that is when the organization has no owner or admin and no other member holds an admin grant. An agent's admin grant does not count: agents get their access from people. Because the API never leaves an organization without an owner (`last_owner`), this cannot happen through the API today; the rule guards the data against states reached another way (a deleted user). The only admin grant of a project can therefore normally be revoked, also by its holder: the organization's owners and admins remain.
- **Unknown grant id**, or a grant of another project → 404 `Grant not found`.
- **Rule placement**: `project_stays_administrable(session, project, without)` lives in `todolist.permissions`; `services/project_grants.py` (`list_project_grants`, `set_project_grant`, `revoke_project_grant`) applies it and raises the errors. The project row is locked during the check.

## Lists (2026-11-14, US-013)

- **Table**: `todo_lists` with `project_id` (cascade, indexed), `name` (200), `description` (text, nullable), `mode` (`human_only | ai_only | mixed`, PostgreSQL type `list_mode`), `position` (integer), `created_by` (the user; null when that user is deleted or when an agent created the list) and timestamps. Model `TodoList`, enum `ListMode`.
- **Names and descriptions** follow projects: trimmed, name 1 to 200 characters and not unique, description at most 2000 characters, an empty one stored as null.
- **Routes**: `POST` (201) and `GET /api/projects/{project_id}/lists` create and list; `GET`, `PATCH` and `DELETE` (204) `/api/lists/{list_id}` address a list by its own id.
- **Shape**: `{id, project_id, name, description, mode, position, created_by, created_at, updated_at}`. `PATCH` changes only the fields that are sent: `description: null` clears it, `name: null` and `mode: null` are a 422. A list cannot move to another project.
- **Default mode**: decided when the list is created (`mode` left out or null): `mixed` when the project's organization has at least one agent at that moment, otherwise `human_only`. Existing lists never change mode by themselves when agents are added or deleted.
- **Position**: a new list goes after the last one of its project (highest position + 1, starting at 1; the project row is locked while it is picked). The index is ordered by position, then age. Deleting a list leaves a gap; v1 has no story for reordering lists, so positions are ordered but not gap-free.
- **Access**: `effective_list_role(session, principal, todo_list, project)` in `todolist.permissions` is the one rule for a list; until US-014 it returns the role on the list's project. `require_list_role(minimum)` in `todolist.api.deps` (aliases `ListContextDep`, `ListEditorContextDep`, `ListAdminContextDep`) answers 404 `List not found` without a role and 403 `forbidden` when the role is too low. `GET` needs viewer, `POST` and `PATCH` editor, `DELETE` admin. The mode is stored but not enforced yet (US-017).
- **`create_list` takes a `Principal`**, so the MCP tools can share it.

## List ACL (2026-11-14, US-014)

- **Table**: `list_grants`, shaped like `project_grants` with `list_id` instead of `project_id` and `role` `none | viewer | editor | admin` (its own PostgreSQL type `list_role`; `principal_kind` is reused). Model `ListGrant`, enum `ListRole`. Grants are deleted with their list, user or agent.
- **Rule** (`effective_list_role(session, principal, todo_list, project)`): owners and admins of the organization are admin, whatever the grants say. For everyone else the list grant decides when there is one, also against a higher project role (`none` hides the list even from a project admin); without a list grant the project role applies. The result stays a `ProjectRole | None`: `none` and "no role at all" are the same answer (404).
- **A list grant needs a membership too**: it counts only while the user is a member of the organization (the agent belongs to it), and removing a member deletes their list grants in that organization along with their project grants.
- **List-only access**: a principal with a list grant and no project grant can use `/api/lists/{list_id}` according to that grant. The project stays closed to them: `GET /api/projects/{id}`, its grants and creating lists answer 404, and the project is not in the organization's project index. They learn the project's name from the list: the list shape gained `project_name`.
- **List index**: `GET /api/projects/{project_id}/lists` returns the lists the caller can see (`visible_lists(principal, project)` in `todolist.permissions`, the same rule as a query). It answers 404 `Project not found` only when the caller has no role on the project and sees none of its lists; a list-only principal gets just their lists, and someone with a project role whose lists are all hidden gets an empty list.
- **Grants API**: `GET` and `PUT /api/lists/{list_id}/grants`, `DELETE /api/lists/{list_id}/grants/{grant_id}` (204), all list admin (`ListAdminContextDep`), with the shape and answers of the project grants API (`PUT` is create-or-update, 422 `invalid_principal`, 404 `Grant not found`). `role` also takes `none`. `GET` returns the grants on the list itself, not the inherited project roles. Revoking a list grant brings the project role back.
- **No last-admin rule on lists**: the organization's owners and admins are always admin on every list, so a list cannot become unreachable. A list admin can lower or hide their own access.
- **Creating a list** still needs editor on the project; the creator gets no list grant (their project role covers it).

## Items (2026-11-14, US-015)

- **Table**: `items` with `list_id` (cascade), `title` (500), `notes` (text, nullable), `status` (`open | done`, PostgreSQL type `item_status`), `position` (integer), `created_by_kind` + `created_by_id`, `completed_by_kind` + `completed_by_id` (nullable), `completed_at` (nullable) and timestamps; index on `(list_id, position)`. Model `Item`, enum `ItemStatus`. The `*_kind` columns reuse `principal_kind`.
- **Actor columns have no foreign key**: the id points to a user or an agent depending on the kind, and it is a record of who did it. It stays when that user or agent is deleted (the audit log of US-018 keeps the name).
- **Completion matches status**: a check constraint makes `completed_by_kind`, `completed_by_id` and `completed_at` all set on a `done` item and all null on an `open` one. `completed_at` is the database's clock.
- **Completing a done item changes nothing**: it keeps its first completer and time. Only `open → done` records a completion and only `done → open` clears it.
- **Titles** are trimmed, 1 to 500 characters. **Notes** are trimmed, at most 10000 characters; empty notes are stored as null.
- **Routes**: `GET` (viewer) and `POST` (201, editor) `/api/lists/{list_id}/items`; `GET` (viewer), `PATCH` (editor) and `DELETE` (204, editor) `/api/items/{item_id}`. The role is the caller's effective role on the item's list. No role → 404 `List not found` / `Item not found`; too low → 403. `GET /api/items/{item_id}` is not in the story; it is there for symmetry with lists and projects.
- **Shape**: `{id, list_id, title, notes, status, position, created_by: {kind, id}, completed_by: {kind, id} | null, completed_at, created_at, updated_at}`. `PATCH` changes only the fields that are sent: `notes: null` clears them, `title: null` and `status: null` are a 422. Actor names are not in the shape yet; a story that shows them (the UI, the audit log) adds them.
- **Position**: a new item goes after the last one of its list (highest position + 1, starting at 1; the list row is locked while it is picked). Deleting leaves a gap until US-016 makes positions gap-free.
- **Service**: `services/items.py` (`list_items`, `create_item`, `update_item`, `delete_item`); the functions that change something take the acting `Principal`. Like the list service, they trust the caller to have checked the role. The list mode is not enforced yet (US-017).

## Item reordering (2026-11-14, US-016)

- **Route**: `POST /api/items/{item_id}/move {"before_item_id": <uuid> | null}` (editor on the item's list) puts the item just before that item of the same list, or at the end when null. It answers 200 with the moved item in the item shape. The field must be sent: an empty body is a 422, so it cannot move an item to the end by accident.
- **Positions are 1 to n in every list**, without gaps or doubles. `create_item` appends at n + 1, `move_item` shifts the items between the old and the new place by one, `delete_item` shifts the items after the deleted one up. All three lock the list row first, so they cannot interleave. This replaces "deleting leaves a gap" from US-015; the migration renumbers the existing items.
- **Unique in the database**: `uq_items_list_id_position` on `(list_id, position)`, `DEFERRABLE INITIALLY DEFERRED` (it replaces the plain index), so a move can shift rows inside the transaction and a bug that doubles a position fails at commit. Gap-freeness is kept by the service, not by a constraint.
- **Invalid target**: a `before_item_id` that is not an item of the same list is a 422 `invalid_before_item`, whether it is in another list or does not exist (one answer, so it reveals nothing about lists the caller cannot see). An item never moves to another list.
- **No-ops are fine**: moving an item before itself, before the item that already follows it, or to the end when it is last answers 200 and changes nothing (also not `updated_at`).
- **`updated_at`**: a move updates it on the moved item only. The items that shift (by a move or a delete) keep theirs: their content did not change.
- **Service**: `move_item(session, principal, item, before_item_id)` in `services/items.py`; the principal is the actor for the audit log (US-018).

## List mode enforcement (2026-11-14, US-017)

- **One check**: `list_access(session, principal, todo_list, project)` in `todolist.permissions` combines `effective_list_role` with the list mode and the principal kind. It returns None when the list does not exist for the principal (404), otherwise a `ListAccess` (`role`, `mode`, `kind`) that answers `allows(action)` / `require(action)` / `denial(action)` for a `ListAction`: `READ` (viewer), `CHANGE_ITEMS` (editor: create, edit, complete, reopen, move, delete), `EDIT_LIST` (editor: name, description, mode) and `ADMINISTER` (admin: grants, deleting the list). Every list and item route goes through it (`require_list_action` / `require_item_action` in `todolist.api.deps`); MCP tools call it directly. `effective_list_role` stays the role alone and is not a permission check by itself.
- **human_only**: an agent has no `ListAccess`, whatever its grants, and `visible_lists` leaves the list out for agents. Grants for agents on such a list can still be stored; they start to count when the mode changes.
- **ai_only**: a user (also an organization owner or admin) reads according to their role. `CHANGE_ITEMS` is a 403 with code `list_ai_only`. `EDIT_LIST` needs admin on the list instead of editor (403 `list_ai_only` for an editor), so only an admin can switch the mode back; `ADMINISTER` is unchanged. Agents act according to their role.
- **mixed**: both kinds act according to their role.
- **Order of the errors**: the role is checked first, so a viewer gets 403 `forbidden` and an editor or admin gets 403 `list_ai_only`.
- **Not restricted**: an agent with the editor role may change a list's mode like a user with that role (also to `human_only`, which locks the agent itself out). Creating a list is a project permission and has no mode yet.

## Audit event recording (2026-11-14, US-018)

- **Table**: `audit_events` with `organization_id` (foreign key, cascade: the log goes with its organization), `project_id` and `list_id` (nullable, no foreign key), `actor_kind` (`principal_kind`), `actor_id`, `actor_name` (snapshot), `action`, `target_kind`, `target_id`, `details` (JSONB) and `created_at`. Events are only inserted; there is no `updated_at`. Indexes on `(project_id, created_at)` and `(list_id, created_at)`.
- **Recording**: `record_event(session, principal, action, *, target_kind, target_id, project_id, list_id, details)` in `services/audit.py`. It flushes and never commits, so the event is committed or rolled back with the change. The services that make the change call it, not the routes, so the MCP tools record the same events. The organization is `principal.organization_id`.
- **Actions** (`AuditAction`, stored as a string so a new action needs no migration): `project.created | updated | deleted`, `list.created | updated | deleted`, `item.created | updated | completed | reopened | moved | deleted`, `project_grant.set | revoked`, `list_grant.set | revoked`. Target kinds: `project`, `list`, `item`, `project_grant`, `list_grant`.
- **Details**: every event carries the display name of its target at that moment (`name` for a project or list, `title` for an item, `principal: {kind, id, name}` for a grant), so the log is readable after the target is gone. Updates add `changes: {field: {old, new}}` with only the fields that changed; a list mode change is `changes.mode`. `item.moved` has `changes.position`. `list.created` has the `mode`. A grant set has `role: {old, new}` (`old` null for a new grant), a revoke has the `role` that was revoked.
- **Nothing changed, nothing recorded**: a PATCH with the current values, a move that leaves the item in place and a grant set to the role it already has record no event.
- **One PATCH, up to two item events**: `item.updated` for a changed title or notes, `item.completed` / `item.reopened` for a changed status.
- **Cascades record one event**: deleting a project records `project.deleted` only (not its lists, items and grants), deleting a list `list.deleted` only. The admin grant a new project gives its creator is part of `project.created`. Grants that disappear because a member is removed from the organization are not recorded: membership changes are not in the audit log in v1.
- **Service signatures**: every changing function of the project, list, item and grant services takes the acting `Principal` (`actor` in the grant services, where `principal_id` already names the grantee). `create_project(session, principal, name, description)` takes the organization and the creator from the principal.

## Audit log API (2026-11-14, US-019)

- **Routes**: `GET /api/projects/{project_id}/audit` (project admin) and `GET /api/lists/{list_id}/audit` (list admin, `ListAction.ADMINISTER`, so people also read it in an AI-only list). 404 without a role, 403 `forbidden` below admin. An admin of a list only gets 404 on the project's log.
- **Scope**: the project log is every event with that `project_id` (the project itself, its grants, its lists, their grants and items); the list log every event with that `list_id`. Events of a deleted list stay in the project log. Events of an existing list the caller cannot see (a list grant `none` on a project admin, a human-only list for an agent) are left out of the project log, with `visible_lists`.
- **Response**: `{events: [...], next_cursor: string | null}`. An event is `{id, created_at, actor: {kind, id, name}, action, target_kind, target_id, project_id, list_id, details}`; `actor.name` is the snapshot from when it happened.
- **Order and cursor**: newest first by `(created_at, id)`; the id (UUIDv7) orders events of one transaction. `next_cursor` is opaque (base64 of the last event's `created_at` and id) and null on the last page; pass it back as `cursor`. Keyset paging, so new events do not shift later pages. A cursor that cannot be read is a 422 `invalid_cursor`.
- **Parameters**: `limit` (default 50, 1 to 200; outside that range is a 422, not clamped), `cursor`, `actor_kind` (`user | agent`), `actor_id`, `action` (a literal prefix: `item.` gives all item events, `item.completed` one kind; no wildcards). Filters combine with AND.
- **Service**: `project_events(session, principal, project, filters=, limit=, cursor=)` and `list_events(session, todo_list, ...)` in `services/audit.py` return an `EventPage`; the caller checks the admin role first (the route dependencies do, the MCP tools must too).

## OAuth server: storage, metadata and client registration (2026-11-14, US-020)

- **Read first**: the MCP authorization specification, revision 2026-07-28, and the `mcp` Python SDK 2.3 (its authorization docs and the source of `mcp.server.auth` and `mcp.client.auth`).
- **Hand-written endpoints, not the SDK's authorization-server provider.** The SDK's `OAuthAuthorizationServerProvider` / `auth_server_provider=` is not used. Reasons: the SDK docs say it predates the split between authorization server and resource server and that new servers should not use it; its routes run outside FastAPI, so they don't get the request's database session and transaction; its registration handler gives clients a secret by default and its client authentication compares the plain secret, which does not fit hashed storage and public clients; and its `/authorize` has no place for our session check and consent screen with an agent choice. The SDK is used where it fits: its pydantic models `OAuthMetadata` and `ProtectedResourceMetadata` produce the two metadata documents (so they are what the SDK's client parses), and US-023 uses its resource-server side (`TokenVerifier` + `AuthSettings`, bearer middleware, streamable HTTP).
- **Paths** (fixed by the specifications, at the root of the app and not under `/api`): `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-protected-resource` (the same document; MCP clients try the path-suffixed one first, then the root one), `/register`; `/authorize`, `/token` and `/revoke` follow in US-021 and US-022 and are already advertised.
- **Issuer** is `PUBLIC_BASE_URL` without a trailing slash (`Settings.oauth_issuer`); the resource is `<issuer>/mcp` (`Settings.mcp_resource_url`). Clients compare the issuer as a string, so every OAuth URL is built from that property.
- **Authorization server metadata**: issuer, the four endpoints, `response_types_supported: [code]`, `response_modes_supported: [query]`, `grant_types_supported: [authorization_code, refresh_token]`, `token_endpoint_auth_methods_supported` and `revocation_endpoint_auth_methods_supported: [none]`, `code_challenge_methods_supported: [S256]` (clients must refuse a server without it), `scopes_supported: [mcp]`. Both documents are public and cacheable for an hour.
- **Not advertised**: `client_id_metadata_document_supported` (Client ID Metadata Documents are the spec's preferred registration and a SHOULD; v1 has dynamic registration only, which the spec keeps for compatibility and which Claude Code and Codex use) and `authorization_response_iss_parameter_supported` (RFC 9207, a SHOULD). If US-021 adds the `iss` parameter to authorization responses it must set that flag in the same change: a client rejects a response without `iss` once the flag is true.
- **One scope, `mcp`**: "use the lists as the agent picked on the consent screen". What a token may do is decided by the agent's grants, not by scopes. It exists so that the metadata, the `WWW-Authenticate` challenge and the `scope` columns have a defined value.
- **Tables**: `oauth_clients` (`client_id` string primary key, `client_secret_hash` nullable, `redirect_uris` and `grant_types` as text arrays, `client_name`, `scope`, timestamps), `oauth_authorization_codes` (`code_hash`, `redirect_uri`, `code_challenge`, `used_at`), `oauth_access_tokens` and `oauth_refresh_tokens` (`token_hash`, `revoked_at`, `authorization_code_id`). Codes and tokens all have `client_id`, `user_id` (who approved), `agent_id`, `scope`, `resource` (the RFC 8707 resource indicator, nullable) and `expires_at`, and are deleted with their client, user or agent. `authorization_code_id` (set null when the code row is deleted) links every token, also after refreshes, to the code it descends from, so reusing a code can revoke them all (US-022).
- **Hashing**: codes and tokens are 256 random bits (`new_token()`) stored as hex SHA-256 (`hash_token()`), unique per table. No salt or slow hash: the input is random, and the lookup is by hash.
- **Registration** (`POST /register`, RFC 7591) is open to anyone, as the flow requires, and answers 201 with `client_id`, `client_id_issued_at`, `redirect_uris`, `grant_types`, `response_types`, `token_endpoint_auth_method`, `scope` and `client_name` (when given), `Cache-Control: no-store`.
  - **Public clients only**: every client is registered with `token_endpoint_auth_method: none` and no secret, also when it asks for `client_secret_post` or `client_secret_basic` (RFC 7591 lets the server replace requested values; the response says what was registered). `client_secret_hash` stays null; the column is there for a later pre-registered confidential client.
  - **Redirect URIs**: 1 to 10, each at most 2000 characters, absolute, without fragment, credentials, whitespace or control characters, and either `https` with a host or `http` on exactly `localhost`, `127.0.0.1` or `[::1]` (any port). Custom schemes (`myapp://`) are refused. They are stored as sent, for exact comparison in `/authorize`; duplicates are dropped.
  - **Other metadata**: `client_name` is trimmed, at most 200 characters; `grant_types` must include `authorization_code` and may add `refresh_token` (default: both); `response_types` can only be `[code]`; `scope` can only be `mcp`. Fields the server does not use (`client_uri`, `logo_uri`, `application_type`, ...) are ignored and not stored. A JSON `null` counts as absent. The body is at most 16 kB.
  - **Errors** follow RFC 7591: 400 with `{"error": "invalid_redirect_uri" | "invalid_client_metadata", "error_description": ...}`, also for a body that is not a JSON object (not FastAPI's 422).
- **OAuth error shape**: the OAuth endpoints raise `todolist.errors.OAuthError(error, description, status_code=400)`, answered as `{"error", "error_description"}` with `Cache-Control: no-store`, because OAuth clients read that shape. The `/api` routes keep `AppError`.
- **Not done here (no story asks for it)**: rate limiting or cleanup of registrations nobody uses, and CORS headers on the OAuth endpoints (browser-based MCP clients such as the MCP Inspector need them; Claude Code and Codex do not).

## OAuth authorize endpoint and consent API (2026-11-14, US-021)

- **Read first**: the MCP authorization specification (revision 2026-07-28, also its security considerations) and `mcp.client.auth` of the SDK, for what a client sends and checks.
- **`GET /authorize`** checks in this order:
  1. `client_id` (a registered client) and `redirect_uri` (required, and exactly one of the client's registered URIs as a string: no normalization, no prefix match). A problem here answers 400 with a small HTML page and never redirects; that is also the answer without a session.
  2. Everything else, answered by a redirect to the client's redirect URI with `error`, `error_description`, `state` and `iss`: `response_type` must be `code` (`unsupported_response_type`, or `invalid_request` when it is missing); `code_challenge` is required and must be 43 to 128 unreserved characters, with `code_challenge_method=S256` (a missing method would mean `plain`, which is refused): `invalid_request`; `scope`, when sent, can only be `mcp` (`invalid_scope`); `resource`, when sent, must be the MCP endpoint, with or without a trailing slash (`invalid_target`); a parameter given twice is `invalid_request`.
  3. No session: 302 to `/login?next=<the same /authorize URL as a path>`. The login page (US-028) passes `next` on to the sign-in; coming back, the request is validated again. Nothing is stored before the user is signed in.
  4. Session: a pending request is stored and the browser goes to `/oauth/consent?request=<id>` (the SPA page of US-037).
- **`state` is optional**. The story lists it among the validated parameters; the specification only says clients SHOULD use it (PKCE is what protects the code), so a request without it is accepted. When sent it is at most 2000 characters and comes back unchanged in every response, also the errors. A state that is too long or sent twice is `invalid_request` without a `state` in the answer.
- **`iss` (RFC 9207)** is in every authorization response, success and error, and the metadata now says `authorization_response_iss_parameter_supported: true` (the two go together, see US-020). Its value is `Settings.oauth_issuer`.
- **`scope` and `resource` may be left out**: the scope is then `mcp`, the resource stays null on the code. US-022 decides what the token request must repeat.
- **Pending request**: table `oauth_authorization_requests` (client, user, redirect URI, code challenge, state, scope, resource, `expires_at`), valid for 10 minutes and deleted when it is approved or denied, so it is answered once. Only the user who started it can read or answer it; for anyone else, and after it expired or was answered, it is a 404 `Authorization request not found`. The id is a UUIDv7 in the consent URL: it is not a secret, the session is. Expired rows are deleted whenever a new request is stored.
- **Consent API** (under `/api/oauth`, session required, normal `AppError` bodies):
  - `GET /api/oauth/requests/{id}` → `{id, client_name, redirect_host, scope, expires_at, agents: [{id, name, description, organization: {id, name}}]}`. `redirect_host` is the host and port of the redirect URI (the specification requires showing it); `client_name` is what the client registered and may be null. The agents are those of every organization where the user is owner or admin, in the order the user joined the organizations, oldest agent first.
  - `POST .../approve {"agent_id"}` → `{redirect_url}`: the redirect URI with `code`, `state` and `iss`. The code is 256 random bits, stored hashed, valid for 10 minutes, bound to the client, redirect URI, code challenge, scope, resource, the approving user and the agent.
  - `POST .../deny` → `{redirect_url}` with `error=access_denied`.
  - The SPA navigates to `redirect_url`; the API does not redirect itself (a `fetch` cannot follow a redirect to another origin usefully).
- **Agent that may not be authorized**: 403 `forbidden`, the same answer for an agent of an organization the user is not in, one where they are a plain member, and an id that does not exist (so the answer does not reveal which ids exist). This departs from "404 when you can't see it" because the story asks for 403. The request stays pending, so the user can pick another agent.
- **Rule placement**: `can_authorize_agent(session, principal, agent)` and `authorizable_agents(user_id)` in `todolist.permissions`, built on `can_manage_organization`.
- **Not done here**: the error page is plain HTML without styling (it is shown only for a broken or hostile client). The consent API does not tell the SPA whether a redirect URI is loopback; US-037 can derive the localhost warning the specification recommends from `redirect_host`.

## OAuth token endpoint, revocation and token lookup (2026-11-14, US-022)

- **Code**: `todolist.services.oauth_tokens` (`token_request`, `revoke_token`, `resolve_access_token`), routes `POST /token` and `POST /revoke` in `api/oauth.py`. No schema change: the tables of US-020 were enough.
- **Requests** are `application/x-www-form-urlencoded`, parsed by hand (at most 16 kB). Another content type, a parameter sent twice or a missing required parameter is `invalid_request`; a parameter without a value counts as absent (RFC 6749 3.2).
- **Client authentication**: clients are public, so the `client_id` form field identifies the client. A missing or unknown `client_id` is `invalid_client` with status 401 (the status the SDK's own server uses). A client that has a secret (none are created by registration) must send it as `client_secret`.
- **Order of checks at `/token`**: form → `grant_type` (`invalid_request` when missing, `unsupported_grant_type` when it is not `authorization_code` or `refresh_token`) → client (`invalid_client`) → the client registered that grant type (`unauthorized_client`) → the grant itself.
- **Authorization code grant**: `code`, `redirect_uri` and `code_verifier` are required. `invalid_grant` when the code is unknown, belongs to another client, has expired, the redirect URI is not exactly the one of the authorization request, or the verifier does not match (S256; the verifier must be 43 to 128 unreserved characters). A failed attempt does not use the code up. `resource` is optional; when sent it must be the MCP endpoint (`invalid_target`). The token's `resource` is the code's, or else the one of the token request.
- **Response**: `{access_token, token_type: "Bearer", expires_in: 3600, scope: "mcp", refresh_token}` with `Cache-Control: no-store`. A client that registered only `authorization_code` gets no refresh token.
- **Lifetimes**: access token 1 hour, refresh token 30 days; every rotation starts a new 30 days, so a client that keeps working stays connected and one that is idle for a month must authorize again.
- **Code reuse**: a second request with a used code is `invalid_grant` and revokes every access and refresh token that descends from the code, also those from later refreshes (`authorization_code_id`).
- **Refresh**: the old refresh token is revoked and a new access and refresh token are issued. The access token from before the refresh is left to expire. A refresh token that was already rotated or revoked is `invalid_grant` and ends its whole family, including the tokens of whoever refreshed first (OAuth 2.1 reuse detection: the server cannot tell the client from a thief). `scope` may be sent but can only be `mcp`.
- **The error after reuse is returned, not raised**: the request's transaction is rolled back when a handler raises, which would undo the revocation. The service raises `ReplayedGrantError` after revoking, and the route answers with `oauth_error_response(error)` so the transaction commits. A test runs this with a session that rolls back like production.
- **Revocation (RFC 7009)**: `POST /revoke` with `token` and `client_id`; always 200 with an empty body, also for a token that is unknown, already revoked or another client's (that one is left alone). Revoking a refresh token revokes every token of the same authorization; revoking an access token revokes only that one. `token_type_hint` is ignored: both tables are looked up.
- **A token is only as good as the approval behind it**: `resolve_access_token(session, token)` gives the agent's `Principal`, and None for an unknown, expired or revoked token, a deleted agent (the rows are deleted with it), and also when the user who approved the client may no longer authorize that agent (`can_authorize_agent`: left the organization, or no longer owner or admin). Otherwise someone removed from an organization would keep acting in it through the token on their machine. The same check refuses the code exchange and the refresh (`invalid_grant`). Nothing is deleted or revoked for it: when the role comes back, tokens that have not expired work again. This answers the open question of US-020.
- **Not done here (no story asks for it)**: deleting expired codes and tokens, rate limiting, token introspection, and audit events for issuing or revoking tokens.

## MCP server with bearer authentication (2026-11-14, US-023)

- **Read first**: the SDK's docs "Add to an existing app" and "Authorization", the source of `mcp.server.mcpserver`, `mcp.server.lowlevel.server.streamable_http_app`, `mcp.server.auth.middleware` and `mcp.server.transport_security` (SDK 2.3), and the MCP authorization specification (revision 2026-07-28) on what a resource server answers.
- **Where**: package `src/todolist/mcp_server/` (not `todolist.mcp`, which reads like the SDK). `create_mcp_server(settings, session_scope)` builds one SDK `MCPServer` per app (a session manager can run only once, so no module-level server); `create_app` adds its ASGI app as a plain Starlette `Route("/mcp")`, not a mount. A mount at `/mcp` would redirect `/mcp` to `/mcp/`, and the mount at `/` from the SDK docs would swallow every unmatched path, which the SPA needs later. The app's lifespan runs `mcp_server.session_manager.run()`.
- **Stateless, JSON responses** (`stateless_http=True`, `json_response=True`): every request stands alone and carries the bearer token, nothing is kept in memory between requests, any worker can answer and a restart loses nothing. The tools are short request/response calls; none needs a server-to-client request or a stream. Clients on the 2026-07-28 protocol and on the older initialize handshake both work (tested with the SDK client in `auto` and `legacy` mode).
- **Authentication is the SDK's resource-server side**: `token_verifier=AgentTokenVerifier` + `AuthSettings(issuer_url, resource_server_url, required_scopes=[mcp])`. The verifier calls `resolve_access_token` in its own short transaction and returns an `AgentAccessToken` (the SDK's `AccessToken` plus the agent `Principal`), on every HTTP request, so a revoked or expired token or a withdrawn approval stops working at the next request. Without a valid token the SDK answers 401 with `WWW-Authenticate: Bearer error="invalid_token", error_description=..., resource_metadata="<issuer>/.well-known/oauth-protected-resource/mcp"`; that URL is the document from US-020 (the SDK's own copy of that route is never reached). A browser session cookie is not a login at `/mcp`.
- **`validate_token_resource=False`**: the token store holds only tokens issued by this app for this one MCP endpoint (`/authorize` and `/token` refuse any other `resource`), so there is no other audience to refuse, and a token whose client never sent `resource` has a null one, which the SDK's check would reject.
- **No `scope` parameter in the challenge**: the specification says SHOULD; the SDK's middleware does not send it and clients then use `scopes_supported` from the metadata, which is the same single scope `mcp`. Not worth replacing the SDK's middleware for.
- **`AccessToken.client_id` and `subject` are the agent's id**: `resolve_access_token` gives the agent, not the OAuth client, and in stateless mode the SDK uses these fields only to name the caller.
- **Tool handlers** get `agent_context` (made by `agent_context_factory(session_scope)`, passed to `register_tools`): `async with agent_context() as ctx` gives `ctx.principal` and `ctx.session`, one transaction per tool call, committed when the block ends and rolled back when it raises (the same rule as a route). Sessions are opened through `app.state.session_scope` (`todolist.db.transaction(session_factory)`), which the tests replace with the shared test session.
- **DNS rebinding protection** (the SDK's `TransportSecuritySettings`): `/mcp` only answers requests whose `Host` is the host of `PUBLIC_BASE_URL` (421 otherwise) and whose `Origin`, when sent, is that origin (403 otherwise). Outside production `localhost`, `127.0.0.1` and `[::1]` on any port are allowed too. A deployment behind a proxy that rewrites `Host` must set `PUBLIC_BASE_URL` to what the app receives, or keep the header.
- **`whoami`** returns `{agent_id, name, organization: {id, name, slug}, accessible_list_count}` as structured content (and the same JSON as text). The count uses the new `accessible_lists(principal)` in `permissions.py`: the rules of `list_access` for all projects of the organization at once; `visible_lists(principal, project)` is now that query narrowed to one project.

## MCP read tools (2026-11-14, US-024)

- **Read first**: `mcp.server.mcpserver.exceptions` and `tools/base.py` of the SDK (2.3) for how a tool reports a failure.
- **Tools**: `list_projects()` → `{projects: [{id, name, description}]}`; `list_lists(project_id?)` → `{lists: [{id, name, description, mode, project: {id, name}, role, open_item_count, done_item_count}]}`; `get_list(list_id, include_done=false)` → the same list object plus `items: [{id, title, notes, status, position, created_at, updated_at, completed_at}]`. Results are an object with one named array, not a bare array (the SDK would wrap that in `{result: [...]}`).
- **`list_projects` follows the lists, not the project grants**: a project is there when the agent sees at least one list in it (`projects_with_accessible_lists(principal)` in `permissions.py`, built on `accessible_lists`). A list grant alone is enough; a project role on a project whose lists are all human-only or closed with a `none` grant, or that has no lists, is not.
- **`list_lists(project_id)`** uses the rule of the HTTP list index: the project exists for the agent when it has a role on it or sees a list in it. So a project the agent has a role on but no visible list in gives an empty result, although `list_projects` leaves it out. Any other id is the error `Project <id> not found`.
- **Order**: projects oldest first; lists by project (oldest first), then position; items by position. `role` is the agent's effective role on the list (`viewer | editor | admin`) from `list_access`, asked once per list.
- **Counts** are of all items, so with `include_done=false` `done_item_count` says how many items were left out.
- **Errors**: an `AppError` raised inside `agent_context()` becomes the SDK's `ToolError` with the error's `detail` (the transaction is rolled back first), so tools raise the same errors as routes and the services need no MCP variant. The agent gets `is_error` with `Error executing tool <name>: <detail>` (the SDK adds the prefix). Any other exception is a crash: the SDK logs it and the agent sees only `Error executing tool <name>`. Arguments that do not fit the schema (a malformed id) are reported by the SDK with pydantic's message.
- **Not found** is one message for a list or project that does not exist, is in another organization, is not shared with the agent, or is human-only: `List <id> not found: it does not exist or you have no access to it. Call list_lists for the lists you can use.`

## MCP write tools (2026-11-15, US-025)

- **Tools**: `add_item(list_id, title, notes?)`, `update_item(item_id, title?, notes?)`, `complete_item(item_id)`, `reopen_item(item_id)`, `move_item(item_id, before_item_id?)` and `delete_item(item_id)`. The first five return the item (`{id, list_id, title, notes, status, position, created_at, updated_at, completed_at}`); `delete_item` returns `{id, list_id, title}` of what is gone.
- **Same services**: the tools call `create_item`, `update_item`, `move_item` and `delete_item` of `services/items.py` with the agent's `Principal`, so positions, completion and audit events are those of the HTTP API. The title and notes constraints (`ItemTitle`, `ItemNotes`) moved from `api/items.py` to `services/items.py` and type the tool parameters too.
- **Permission**: every write tool asks `list_access(...).require(ListAction.CHANGE_ITEMS)` (editor). A viewer agent gets `Error executing tool <name>: This needs the editor role on the list`. An item that does not exist, or whose list the agent cannot see (not shared, human-only, `none` grant), is one message: `Item <id> not found: it does not exist or you have no access to its list. Call get_list for the items of a list.`
- **`update_item` notes**: a tool call cannot tell a left-out argument from null, so leaving `notes` out keeps them and an empty string removes them. A call with neither `title` nor `notes` is an error (`Nothing to change: pass title, notes or both.`); a call that sets the values the item already has succeeds and records no event.
- **`complete_item` / `reopen_item`** on an item that already has that status succeed and change nothing (the rule of `update_item` in the service), so an agent can repeat them safely.
- **`move_item`** without `before_item_id` moves the item to the end, like `before_item_id: null` in the HTTP API.

## Frontend scaffold and serving the build (US-027)

- **Versions**: Vite 8, React 19, React Router 8 (the `react-router` package, declarative `<Routes>`), Tailwind CSS 4 through `@tailwindcss/vite` (no `tailwind.config`, no PostCSS), Vitest 5 with jsdom and Testing Library, ESLint 10 flat config with typescript-eslint, react-hooks and react-refresh. TypeScript is pinned to 6.0: the Vite template ships TypeScript 7 with oxlint, but the story asks for eslint and typescript-eslint does not accept TypeScript 6.1 or newer yet. TanStack Query and the generated API types come with the API client (US-028).
- **Product name in the frontend**: the constant `APP_NAME` in `frontend/src/config.ts`, set to `Naezlo` (the name the README got in the commit "rename to Naezlo"). The page title is set from it in `main.tsx`. The backend default `Settings.app_name` is still `todolist`; set `APP_NAME=Naezlo` in the environment, or change the default in a later story, to make the API title match.
- **Dev proxy**: Vite proxies `/api`, `/authorize`, `/token`, `/register`, `/revoke`, `/.well-known` and `/mcp` to `http://localhost:8000` without rewriting the Host header. The browser's origin is `http://localhost:5173`, so `PUBLIC_BASE_URL` must be that in development with the dev server (Google redirect URI, OAuth issuer, the MCP server's allowed Host).
- **Serving the build**: setting `FRONTEND_DIST` (default `frontend/dist`, relative to the working directory). When it has an `index.html` at startup, `create_app` adds one last route (`todolist.frontend.install_frontend`); the check is done once, so restart the backend after the first build. The route matches only GET and HEAD, and never a backend path (`/api`, `/authorize`, `/token`, `/register`, `/revoke`, `/.well-known`, `/mcp`, `/healthz`, `/docs`, `/redoc`, `/openapi.json`, each as a whole path segment), so an unknown backend path keeps FastAPI's JSON 404 and a POST to a frontend path is a 404, not a 405. It is a route and not a `StaticFiles` mount at `/`, which would swallow every unmatched path (see the MCP server section).
- **What the route answers**: an existing file of the build is served as is (a path that resolves outside the build is not); a missing path under `/assets/` is a JSON 404, so a stale tab never gets HTML where it expects a script; everything else gets `index.html` for React Router. `Cache-Control` is `public, max-age=31536000, immutable` under `/assets/` (Vite's hashed file names) and `no-cache` for `index.html` and other files.
- **Tests**: the test settings set `frontend_dist=None`, so a local build cannot change backend test results; `tests/test_frontend.py` builds a small fake `dist` in a temporary directory. One test reads `frontend/vite.config.ts` to keep the proxy list and the backend's list equal.

## API client, login page and auth guard (US-028)

- **Generated types**: `npm --prefix frontend run gen:api` runs `python -m todolist.openapi` (the schema of `create_app` with default settings, independent of `.env` and the environment), saves it as `frontend/openapi.json` and runs openapi-typescript on it to write `frontend/src/api/schema.d.ts`. Both files are committed. `tests/test_openapi.py` compares the saved schema with the code, so a backend change without a regeneration fails the backend tests; no Node is needed for that check.
- **openapi-typescript and TypeScript 6**: openapi-typescript 7.13 declares a peer dependency on TypeScript 5. `package.json` has an `overrides` entry that gives it the project's TypeScript (6.0); the generator works with it. Remove the override when a release accepts TypeScript 6.
- **Fetch wrapper**: openapi-fetch (`api` in `src/api/client.ts`) typed with the generated `paths`, plus `unwrap()`, which returns the body or throws an `ApiError` (`status`, `code`, `message`). The message is the backend's `detail`, the first message of a FastAPI validation error, or a generic text; a failed connection is status 0, code `network_error`.
- **Session state** is the TanStack Query entry `['me']`: the `/api/me` body, or null when the answer is 401. A 401 on any other query or mutation sets it to null, so an expired session leads to the login page. Queries retry twice, but never on a 4xx.
- **Guard**: every route except `/login` is inside `RequireAuth`, also unknown paths. A signed-out visitor goes to `/login?next=<path+query+hash>` (plain `/login` for `/`). When `/api/me` fails with something other than 401, the guard shows the error with a retry button instead of the login page.
- **Login page**: shows what `/api/config` allows: a "Sign in with Google" link styled as a button to `/api/auth/google/login?next=...` (a navigation, not a fetch), the dev-login form, both, or a text that no sign-in method is set up. `?error=<code>` from the Google routes is explained in words. A signed-in visitor is sent on to `next` or `/`. `next` is checked with the same rule as the backend's `safe_next_path`; a `next` on a backend path (`/authorize?...` from an MCP client) is opened with a full page load, others with the router.
- **Sign-out** posts `/api/auth/logout`, clears the cached data and goes to `/login` without `next`.
- **Errors** are shown by one component, `ErrorMessage` (inline, `role="alert"`), not a toast.
- **User menu and layout**: `AppLayout` (a header with the product name and the user menu) wraps the guarded pages. It is minimal; the app shell story (US-030) builds on it.

## End-to-end tests (2026-11-15, US-029)

- Playwright (`@playwright/test`, Chromium only, headless) lives in `frontend/`; specs in `frontend/e2e/`. `npm --prefix frontend run e2e` builds the frontend and Playwright starts the backend with `python -m todolist.e2e`, which serves the build itself (the production setup, no Vite dev server).

## App shell and organization switcher (2026-11-15, US-030)

- **Routes**: every page of an organization is under `/o/:orgSlug/...` (the slug, not the id: it never changes after creation, also not on a rename). `/o/:orgSlug` itself is a small start page with the organization's name until the project pages exist. A slug the user is not a member of shows "Organization not found" inside the top bar, without a sidebar.
- **`/`** redirects to the organization this browser showed last, or to the user's first one (the default organization) when that is unknown or the user is no longer in it. "Last used" is kept in the browser (`localStorage`, key `lastOrganization`), not on the server: it needs no API or schema change, at the cost of not following the user to another device. A user without any organization gets a start page with a "New organization" button instead.
- **Layout**: `AppLayout` has the top bar (menu button below the `md` width, product name, organization switcher, user menu) and, on organization pages, the sidebar with the projects from `GET /api/orgs/{id}/projects` (which already returns only what the user can see). Below `md` (768px) the sidebar is a drawer that the menu button opens; choosing a project or pressing next to it closes it.
- **Switcher**: lists the organizations of `/api/me`; choosing one goes to its start page (`/o/<slug>`), not to "the same page in the other organization", which rarely exists. "New organization" opens a dialog that posts `/api/orgs`, adds the answer to the cached `/api/me` data and goes to the new organization.
- **Project links** in the sidebar go to `/o/<slug>/projects/<id>`; that page comes with US-032 and is the layout's "Page not found" until then.
- **Menus** (user menu, switcher) close on Escape, on a press outside and when the focus moves out (`useDismiss`). The earlier "close on blur" closed the menu before the click arrived in Safari, which does not focus a clicked button.
- **Slug race (backend fix)**: `unique_slug` now takes a transaction-level PostgreSQL advisory lock (`SLUG_LOCK_KEY`) before it looks for a free slug. Without it two people with the same name signing up at the same moment picked the same slug and one got a 500 from the unique constraint; the parallel browser tests (all "Ada Lovelace") hit that. Creating organizations is rare, so one lock for all slugs is enough.

## Organization settings page (US-031)

- **Where**: `/o/:orgSlug/settings`, reached from a "Settings" link at the bottom of the sidebar (its own `nav` named "Organization"). No backend change: the page uses the existing organization, member and invitation routes.
- **Who sees what**: every member sees the name and the members table. Owners and admins also get the rename form, the role selectors, the remove buttons and the invitations section; a plain member never asks for the invitations (the API answers 403 there) and gets one line that says only owners and admins can change the settings.
- **Controls follow the API's rules, the API still decides**: an owner gets a selector (owner, admin, member) on every row; an admin gets one (admin, member) on rows that are not an owner and no controls on an owner's row. Everyone has "Leave" on their own row. The selector shows the stored role, so a refused change (such as `last_owner`) falls back by itself and the API's `detail` is shown above the table.
- **Remove and leave ask first**, in the row itself ("Yes, remove" / "Cancel"), not with a browser dialog. Revoking an invitation does not ask: inviting again is one step.
- **After leaving** the organization is taken out of the cached `/api/me` and the app goes to `/`, which leads to another organization or the empty start.
- **The note after inviting** is the `message` of the API's answer, so the two outcomes (invited, or added at once because the account exists) are worded in one place.

## Projects in the UI (2026-11-15, US-032)

- **Address**: a project's page is `/o/:orgSlug/p/:projectId` (the story's path). This replaces the `/o/<slug>/projects/<id>` that the sidebar links of US-030 pointed to; nothing answered there yet.
- **The API tells the caller's role**: `ProjectOut` has `role` (`viewer | editor | admin`, the effective role, so an organization owner or admin gets `admin`) on every project route, also in the list of an organization (`effective_project_roles` in the permission service: the rules of `effective_project_role` for several projects at once). The UI only uses it to hide controls: "Edit" from editor, "Delete" from admin. The API still decides.
- **Open item count**: `ListOut` has `open_item_count` (items that are not done) on every list route, so the project page needs one request for its lists.
- **Project page**: name, description, and the lists as rows with the name, a mode badge ("Human only" since US-033, "AI only", "Mixed") and "n open items". The rows are not links until the list view exists (US-034); creating a list comes with US-033. A project that the API answers 404 for, or one of another organization than the one in the address, shows "Project not found".
- **New project** is a button under the projects in the sidebar, for every member (every member may create a project). The dialog asks for a name and an optional description; the new project is opened.
- **Edit** is one dialog for the name and the description (an emptied description is removed). **Delete** asks in a dialog that names the project and says its lists and items go with it; afterwards the app goes to the organization's start page.
- **Sidebar without a reload**: the three mutations write their answer into the cached project list of the organization (and the cached project), instead of asking for the list again.

## Lists in the UI (2026-11-15, US-033)

- **What the UI may offer comes from the API**: `ListOut` has `role` (the caller's effective role on the list) and `actions` (the `ListAction`s the caller may do: `read`, `change_items`, `edit_list`, `administer`), computed by `ListAccess.actions`. The frontend shows "Edit" for `edit_list` and "Delete" for `administer` (`listAllows` in `frontend/src/lists/hooks.ts`) and does not repeat the role and mode rules. For a project's list index the accesses come from `list_accesses(session, principal, project, todo_lists)` in `permissions.py` (the rules of `list_access` for several lists in a fixed number of queries; a test compares the two).
- **Default mode for the form**: `ProjectOut.default_list_mode` is what `default_list_mode` gives for the project's organization at that moment. The "New list" dialog preselects it, asks for the project again when it opens (an agent may have been added since the page loaded) and always sends the shown mode.
- **Mode labels**: "Human only", "AI only", "Mixed" (the story's wording; the badge said "Humans only" before). Labels and explanations live in `frontend/src/lists/modes.ts`. The badge (`ModeBadge`) has an icon per mode and a tooltip (`role="tooltip"`, linked with `aria-describedby`) that shows on hover and on keyboard focus; the same explanations stand next to the choices in the dialogs.
- **List controls**: "New list" for project editors; per row "Edit" (name, description, mode in one dialog; only the changed fields are sent) and "Delete" (confirmation dialog). Controls that are not allowed are hidden. Rows show the description under the name. Rows are still not links (US-034).
- **Cache updates after a mutation**: `applyToCache(client, key, update)` (`frontend/src/api/queryClient.ts`) cancels a fetch of that query that is still under way before it changes the cached data, and refetches when there is no data yet. Without it a fetch that started before the change could bring the old state back (TanStack Query reuses a running first fetch on `invalidateQueries`). `useInvite` cancels before it invalidates for the same reason.
- **Router without transitions**: `<BrowserRouter useTransitions={false}>`. React Router 8 wraps navigations in `startTransition` by default, so a cache change made next to a `navigate(...)` rendered first; after a sign-out the guard then sent the browser to `/login?next=<the page left>`. `useSignOut` now gives the caller a `forget` function to call right after `navigate('/login')`.


## List view with items (2026-11-15, US-034)

- **Address**: `/o/:orgSlug/l/:listId` (`listPath` in `frontend/src/orgs/paths.ts`, `src/pages/ListPage.tsx`); the list names on the project page link to it. `ListOut` got `organization_id`, so the page answers "List not found" for a list of another organization, as the project page does. The parent project is a link when the project is among the user's visible projects (the sidebar's query) and plain text for someone who only has a grant on the list.
- **One change type, applied optimistically**: every item change is an `ItemChange` (`add | update | move | delete`) sent through `useChangeItems(list, userId, onError)` (`frontend/src/items/hooks.ts`). `applyItemChange(items, change, userId, saved?)` is a pure function that gives the expected list (shown at once) and, with the server's answer, the confirmed one; it is idempotent, so confirming is safe after a refetch. On a rejection the cache goes back to the snapshot taken before the change, the error is shown above the items (`ErrorMessage` with "Dismiss", cleared by the next change) and the items are fetched again.
- **Requests of one list are serial**: the mutation has `scope: { id: 'items-of-<list id>' }`, so TanStack Query sends the changes one after another in the order they were made (two quick additions keep their order) while `onMutate` still runs at once. An item that is not stored yet has an `unsaved-…` id (`isUnsaved`) and its controls are switched off until the server answered.
- **Layout**: the add field is at the top (Enter or "Add"; it keeps the focus) and new items go to the end of the list, as in the API. Open items are one list; done items are in a "Done (n)" section that is folded by default, struck through, without move buttons. Moving works among the open items: "up" puts the item before the previous open one, "down" before the item that follows the next open one, so done items in between keep their place. After a move the focus is put back on the pressed button (or on the opposite one at the top or bottom, where the pressed one is switched off). No drag and drop.
- **Editing**: the title is a button that becomes a text field (Enter or leaving saves, Escape cancels, an empty title is not saved); "Notes" opens a text area with "Save notes" / "Close" (empty notes are removed, `notes: null`); "Delete" asks in the row ("Yes, delete" / "Cancel").
- **Read-only**: without `change_items` in `ListOut.actions` the page has no field, checkboxes or buttons (a "Notes" button only where there are notes) and shows a notice (`role="note"`): "AI agents manage this list…" on an AI-only list, otherwise "You can read this list…".
- **Agent marker**: `created_by.kind === 'agent'` shows "Added by an agent"; a done item with `completed_by.kind === 'agent'` shows "Completed by an agent". The agent's name is not shown (`ItemOut` has only the kind and the id).

## Sharing dialogs (2026-11-15, US-035)

- **Where**: a "Share" button in the header of the project page (project admins) and of the list page (callers whose `ListOut.actions` has `administer`). Both open a dialog (`frontend/src/components/ShareDialogs.tsx`) on the existing grants API. The list rows on the project page get no Share button: the story asks for the two pages.
